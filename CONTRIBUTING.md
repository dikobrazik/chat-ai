# Как мы вносим изменения

Коротко о главном:

```
ветка → Pull Request → ревью → squash merge в main → автодеплой в прод
```

**Merge в main = релиз на прод.** После merge GitHub Actions сам собирает Docker-образ и выкатывает его на сервер в Yandex Cloud. Поэтому в main напрямую не пушим — вообще никогда. Все изменения едут через Pull Request.

---

## Как внести изменение: по шагам

### 1. Создай ветку от свежего main

```bash
git checkout main
git pull
git checkout -b feat/название-фичи
```

Имя ветки — по смыслу изменения:

| Префикс | Когда использовать | Пример |
|---|---|---|
| `feat/` | новая функциональность | `feat/chat-history` |
| `fix/` | исправление бага | `fix/broken-login-button` |
| `chore/` | всё остальное: конфиги, зависимости, рефакторинг | `chore/update-biome` |

### 2. Делай изменения и коммить

Коммитов в ветке может быть сколько угодно — при merge они всё равно склеятся в один (squash). Так что коммить спокойно, хоть после каждого рабочего шага:

```bash
git add .
git commit -m "что сделано"
git push -u origin feat/название-фичи
```

### 3. Открой Pull Request в main

На GitHub появится кнопка «Compare & pull request» — или создай PR руками. В описании напиши **что** поменялось и **зачем** (пара предложений, можно со скриншотом, если менялся интерфейс).

### 4. Дождись зелёного CI и approve

На каждый PR автоматически запускаются проверки:

- **lint** — biome, проверяет **только изменённые в PR файлы** (в старом коде есть известные lint-ошибки, они не блокируют)
- **typecheck** — `tsc --noEmit`, проверка типов TypeScript
- **build** — `next build`, что проект вообще собирается

Если что-то красное — merge заблокирован. Чини в той же ветке, пуш — проверки перезапустятся сами.

### 5. Squash merge

После approve жми **«Squash and merge»** (именно его, не обычный merge). Все коммиты ветки склеятся в один аккуратный коммит в main. Дальше автодеплой сделает всё сам — через несколько минут изменение будет на проде.

Ветку после merge можно удалить — GitHub сам предложит.

## Кто что ревьюит

- **PR от Rafael** ревьюит **dikobrazik** — обязательно. Без его approve merge не пройдёт.
- **dikobrazik** может мержить свои PR сам, без чужого approve (у админа репозитория есть bypass). Но PR он всё равно открывает — так в истории видно, что и когда менялось, и Rafael в курсе изменений.

---

## Чек-лист перед открытием PR

- [ ] Линт твоих изменений проходит: `npx biome ci --changed --since=main` (полный `npm run lint` сейчас краснеет из-за старого кода — это нормально, чинить его в своём PR не нужно)
- [ ] Приложение запускается и работает: `npm run dev`, открыть [http://localhost:3000](http://localhost:3000) и глазами проверить то, что менял
- [ ] В описании PR понятно написано, **что** поменялось и **зачем**

Если lint ругается на форматирование — часто помогает `npm run format` (автоформатирует код).

## Как запустить проект локально

Понадобится Node.js (на проде используется Node 24 — лучше поставить его же) и npm.

```bash
# 1. Установить зависимости (первый раз или после обновления package.json)
npm ci

# 2. Запустить дев-сервер
npm run dev
```

Открой [http://localhost:3000](http://localhost:3000) — приложение перезагружается само при изменении кода.

Проект читает настройки из файла `.env` в корне (адрес бэкенда и т.п.). Этого файла нет в репозитории.

Если делаешь только фронтенд и локального бэкенда у тебя нет — рабочий `.env`:

```bash
NEXT_PUBLIC_BASE_URL=http://localhost:3000
DEV_API_PROXY=https://jonu.ru
```

Dev-сервер будет сам проксировать `/api/*` на прод-бэкенд (см. `rewrites` в `next.config.ts`) — браузер работает same-origin, CORS не мешает. На прод-сборку это не влияет: без `DEV_API_PROXY` прокси выключен. Если нужен другой бэкенд (локальный или тестовый) — спроси `.env` у dikobrazik.
